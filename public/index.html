Introduction

I take a project from the first conversation to a live deployment: the interface people use, the API behind it, and the database that holds it together.

My approach is to understand the problem before writing code, keep the architecture simple enough to explain, and ship something that works in production, not only on my own machine.

I build websites for clients, such as the Imperial Shelter-Tech Konsult site, and products of my own. Veyra and Amoura are both still in development, and this site says so.

How I work

Five habits, each one visible in a project above. If a project is not ready, I say so and describe it as what it is.

  1. 01

    Understand the problem first

    Before any code, I work out who the product is for and what must be true when it ships. Imperial's visitors needed to see past work and ask for a quote without already having a phone number, so those two things came first.

    Seen in Imperial Shelter-Tech Konsult

  2. 02

    Keep the architecture explainable

    Supabase gave Veyra a database, authentication and access rules in one place, which suits one developer. I choose tools I can explain, and maintain, without a team behind me.

    Seen in Veyra

  3. 03

    Own the parts that can fail

    Forms, payments and email run on the server. I replaced a hosted form service on the Imperial site with a route of my own, so validation, delivery and failure handling are in my control.

    Seen in the Imperial contact route and in this site's form

  4. 04

    Audit before release

    A production readiness audit of the Imperial site found missing security headers and no rate limiting on the contact route. I fixed both. Releases go to Vercel only after a diff check and a production build.

    Seen in Imperial Shelter-Tech Konsult

  5. 05

    Say what is not ready

    Veyra and Amoura are still in development. Each case study separates what is built from what is in progress, so nothing is described as finished before it is.

    Seen in every case study
